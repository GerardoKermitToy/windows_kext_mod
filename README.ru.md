# Модифицированное расширение ядра Windows Portmaster

Этот репозиторий содержит модифицированную версию исходного расширения ядра Windows Portmaster. **Версия 3.0.0.0 не совместима по API с исходным расширением ядра Windows Portmaster.** И драйвер, и его клиент пользовательского режима должны поддерживать описанный ниже формат событий подключения версии 3.

Модифицированный драйвер реализован на Rust как сетевой драйвер Windows KMDF без PnP с `no_std`. Он регистрирует обработчики вызовов (callouts) Windows Filtering Platform (WFP), перехватывает трафик IPv4 и IPv6, делегирует решения по пакетам процессу пользовательского режима, кэширует вердикты, блокирует или разрешает трафик и собирает статистику пропускной способности TCP/UDP.

## Версия API и совместимость

Текущая версия API — **3.0.0.0**, она хранится как `[3, 0, 0, 0]` в [windows_kext/kextinterface/version.txt](windows_kext/kextinterface/version.txt) и возвращается посредством `IOCTL_VERSION` как четыре необработанных байта.

Это **нарушающее совместимость изменение API**, а не готовая замена исходного драйвера или клиентов, использующих устаревшую компоновку события подключения:

- `ConnectionIpv4` теперь использует `info_type = 7`, а `ConnectionIpv6` использует `info_type = 8`. Значения `1` и `2` остаются зарезервированными для устаревшего формата; драйвер версии 3 этот формат не выдаёт.
- Оба события подключения включают `tid: u64`, `compartment_id: u32`, `condition_flags: u32`, `interface_index: u32` и `sub_interface_index: u32` сразу после `process_id`. Их фиксированные размеры полезной нагрузки теперь составляют 59 байт для IPv4 и 83 байта для IPv6.
- Прежние `IOCTL_GET_THREAD_ID` (`0x9C40E008`) и метод C++ `Driver::GetThreadId` были удалены. Считывайте `Connection::tid` непосредственно из декодированного события; поиск посредством IOCTL для каждого запроса не нужен.
- Пути к устройству, пятибайтовое обрамление событий, идентификаторы и компоновки команд, значения вердиктов и форматы событий журнала, завершения подключения и пропускной способности не изменились. Эти неизменённые части **не** делают полный API совместимым с исходной реализацией.

Обновляйте драйвер и клиент одновременно. Клиенты должны проверять `IOCTL_VERSION` и поддерживать соответствующие идентификаторы событий и компоновки до обработки трафика. Устаревший клиент может отклонять или игнорировать новые запросы решения и оставлять удержанные пакеты без вердиктов. Если не указано иное, далее ссылки на «драйвер» означают эту модифицированную реализацию версии 3.

Компоновка подключения включает `condition_flags` сразу после `compartment_id`; она несовместима с более ранними сборками версии 3, в которых это поле отсутствовало. Идентификаторы событий остаются `7`/`8`, поэтому драйвер и клиент должны использовать одну и ту же компоновку; один лишь `IOCTL_VERSION` не отличает эти более ранние сборки.

Драйвер и его контроллер пользовательского режима работают как одна система:

- `windows_kext/driver` — драйвер и обработчики вызовов WFP;
- `windows_kext/protocol` — источник истины для двоичного протокола;
- `windows_kext/wdk` и `windows_kext/c_helper` — обёртки вокруг WDK, KMDF, WFP и NDIS;
- `windows_kext/kextinterface` — эталон устаревшего протокола Go и общий файл версии драйвера; его декодер событий подключения Go не был перенесён на API версии 3;
- `kext_client` — клиентская библиотека C++ и `kext_monitor`, обновлённые для API версии 3.

Путь пакета через WFP подробно описан в [windows_kext/PacketFlow.md](windows_kext/PacketFlow.md). Этот документ определяет полный внешний API драйвера: управляющее устройство, `ReadFile`/`WriteFile`, IOCTL, команды, события и значения перечислений. Внутренние функции Rust не являются частью API драйвера.

## Ключевые свойства

Драйвер создаёт 16 обработчиков вызовов WFP:

- авторизация ALE для исходящих и входящих TCP/UDP-подключений через IPv4 и IPv6;
- обработчики закрытия конечной точки ALE для отслеживания времени жизни подключения;
- обработчики ALE об установленном потоке для атрибуции PID и отслеживания времени жизни потока;
- обработчики потоков и датаграмм для статистики пропускной способности TCP/UDP;
- обработчики входящих и исходящих IP-пакетов IPv4 и IPv6.

Новый пакет без постоянного кэшированного решения блокируется и удерживается до ответа процесса пользовательского режима. Пользовательский режим получает событие `ConnectionIpv4` или `ConnectionIpv6` с уникальным ID запроса и отвечает командой `Verdict`. Затем разрешённый клон пакета асинхронно возвращается в сетевой стек через API инъекции WFP.

`Permanent*` в имени вердикта означает, что решение остаётся кэшированным в течение времени жизни этого конкретного экземпляра кэша соединений. Оно не создаёт глобальное правило брандмауэра. Новое подключение, повторно использующее тот же пятиэлементный кортеж после завершения старого подключения, должно получить новое решение.

## Параметры реестра

Драйвер поддерживает необязательное значение `REG_DWORD` по следующему пути:

```text
HKLM\SYSTEM\CurrentControlSet\Services\PortmasterKext\Parameters
```

Только значение DWORD, в точности равное `1`, включает опцию. Отсутствующее значение, другой тип реестра, некорректные данные или любое иное значение DWORD оставляет её отключённой. Значение опции считывается **один раз в `DriverEntry`, до начала фильтрации WFP**. Драйвер не отслеживает изменения реестра; изменение вступает в силу только после выгрузки и повторной загрузки драйвера, а не после повторного открытия устройства или очистки кэша.

| Имя значения | Значение драйвера по умолчанию при отсутствии |
|---|---:|
| `EnableInboundUdpCacheMissPidFallback` | `0` (отключено) |

Этот параметр реестра не добавляет команды и не изменяет проводной протокол драйвера.

### `EnableInboundUdpCacheMissPidFallback`

При включённой опции входящий UDP-пакет IPv4 или IPv6, для которого обычный поиск в кэше соединений не дал результата, может заимствовать PID у первой активной записи UDP, соответствующей `(local_ip, local_port, remote_ip)` в том же семействе IP. `remote_port` донора игнорируется. Если соответствует несколько записей, используется первое активное совпадение; это эвристическая атрибуция PID, а не доказательство владельца сокета пакета.

Если совпадение отсутствует либо выбранный PID равен `0` или `4`, пакет переходит к нативной авторизации `ALE_AUTH_RECV_ACCEPT`. Отключение опции сохраняет этот путь ALE для входящих промахов кэша UDP. Точные попадания в кэш не изменяются.

Успешный резервный вариант создаёт отдельную входящую запись кэша для **точного пятиэлементного кортежа** пакета с заимствованным PID, TID `0`, собственной первоначальной политикой `Undecided` и ID экземпляра соединения. Он не копирует вердикт или время жизни донора и не перезаписывает точную запись, зарегистрированную одновременно. Запрос решения пользовательского режима содержит байты сетевого уровня (`payload_layer = 3`); `PermanentAccept` или другой постоянный вердикт кэшируется для этого нового точного экземпляра, поэтому последующие пакеты с тем же кортежем могут повторно использовать его в любом направлении.

Пока эвристическая запись не связана с нативной конечной точкой UDP, она может истечь после 60 секунд неактивности во время `CleanEndedConnections`. После подключения нативного отслеживания жизненного цикла её временем жизни вместо этого управляет закрытие конечной точки.

Подробности сопоставления и жизненного цикла кэша см. в [windows_kext/INBOUND_UDP_PID_FALLBACK.md](windows_kext/INBOUND_UDP_PID_FALLBACK.md).

Порты `53`, `717` и `719` используют обычный поиск соединений по точному кортежу и обработку
политики. Обходов на основе портов или переписывания адресов/портов нет.

## Доступ к устройству

| Свойство | Значение |
|---|---|
| Имя устройства NT | `\Device\PortmasterKext` |
| Путь Win32 | `\\.\PortmasterKext` |
| Тип управляющего устройства | `FILE_DEVICE_NETWORK` |
| Режим ввода-вывода | Буферизованный ввод-вывод |
| Требуемый доступ | `GENERIC_READ | GENERIC_WRITE` |
| Режим совместного использования | `0` |
| ACL | Полный доступ только для `SYSTEM` и группы Administrators |
| Одновременные клиенты | Один открытый файловый объект |

Второй одновременный запрос `CreateFile` завершается с `STATUS_SHARING_VIOLATION`. Драйвер записывает PID, которому принадлежит дескриптор, и использует его при применении политики к собственному трафику Portmaster.

Для полнодуплексного обмена откройте дескриптор с `FILE_FLAG_OVERLAPPED`. Без этого флага ожидающий `ReadFile` сериализует ввод-вывод на файловом объекте и может не позволить другому потоку выполнить `WriteFile` или `DeviceIoControl`. Каждая операция с дескриптором, открытым для асинхронного ввода-вывода, должна использовать собственную структуру `OVERLAPPED`. Клиенту также следует сериализовать записи, когда команды могут отправляться несколькими потоками.

Пример:

```cpp
HANDLE device = CreateFileW(
    L"\\\\.\\PortmasterKext",
    GENERIC_READ | GENERIC_WRITE,
    0,
    nullptr,
    OPEN_EXISTING,
    FILE_ATTRIBUTE_NORMAL | FILE_FLAG_OVERLAPPED,
    nullptr);
```

Используйте один поток чтения. `ReadFile`, `WriteFile` и все обработчики IOCTL требуют `PASSIVE_LEVEL` внутри драйвера.

## Соглашения о проводном формате

- Протокол двоичный и не содержит выравнивающих заполнителей.
- Каждое многобайтовое целое кодируется в порядке little-endian.
- Адреса IPv4 и IPv6 передаются как 4 или 16 необработанных байтов в сетевом порядке, в том виде, в каком они присутствуют в IP-пакете.
- Порты являются числовыми значениями `u16`, закодированными в проводном формате в порядке little-endian.
- `protocol` — номер IP-протокола IANA, например TCP `6`, UDP `17`, ICMP `1` или ICMPv6 `58`.
- `local_*` идентифицирует локальную конечную точку, а `remote_*` — удалённую конечную точку; эти поля не обязательно являются источником и назначением текущего пакета.
- Потоки команд и событий независимы. Если IOCTL явно не возвращает вывод, принятие команды не порождает синхронный ответ.

## Чтение событий с помощью `ReadFile`

Драйвер предоставляет поток байтов записей. Каждая запись начинается с одного и того же пятибайтового заголовка:

```text
Смещение  Размер  Поле
0         1       info_type
1         4       payload_size (u32 LE)
5         N       payload
```

`payload_size` не включает пятибайтовый заголовок.

Один вызов `ReadFile` может вернуть:

- несколько полных записей;
- одну или несколько полных записей, за которыми следует начало другой записи;
- произвольный фрагмент одной записи.

Клиент должен накапливать байты, пока не получит полный заголовок, а затем ожидать все `5 + payload_size` байты. Границы `ReadFile` не являются границами записей. Неизвестный `info_type` можно пропустить по его объявленной длине полезной нагрузки.

Когда событие недоступно, чтение ожидает. Во время завершения работы уже ожидающее чтение может завершиться как отменённое, а новое чтение после закрытия приёма может завершиться как EOF. Клиент должен трактовать `STATUS_CANCELLED`/`ERROR_OPERATION_ABORTED` и `STATUS_END_OF_FILE`/`ERROR_HANDLE_EOF` как нормальное завершение сеанса, дождаться завершения каждой ожидающей операции `OVERLAPPED` и только затем освободить свой буфер.

### Типы событий

| `info_type` | Имя | Полезная нагрузка |
|---:|---|---|
| `0` | `LogLine` | Уровень важности и текст сообщения |
| `1`, `2` | Зарезервировано | Устаревшие форматы подключений; не выдаются драйвером версии 3 |
| `3` | `ConnectionEndEventV4` | Подключение IPv4 завершено |
| `4` | `ConnectionEndEventV6` | Подключение IPv6 завершено |
| `5` | `BandwidthStatsV4` | Счётчики пропускной способности IPv4 |
| `6` | `BandwidthStatsV6` | Счётчики пропускной способности IPv6 |
| `7` | `ConnectionIpv4` | Запрос решения по пакету IPv4 с метаданными потока выполнения и маршрутизации |
| `8` | `ConnectionIpv6` | Запрос решения по пакету IPv6 с метаданными потока выполнения и маршрутизации |

### `ConnectionIpv4` (`info_type = 7`)

Фиксированная полезная нагрузка составляет 59 байт, за которой следуют захваченные байты пакета. Смещения указаны относительно полезной нагрузки, исключая пятибайтовый заголовок записи:

| Смещение | Размер | Поле | Описание |
|---:|---:|---|---|
| `0` | 8 | `id` | ID запроса для команды `Verdict`; `0` зарезервирован как недопустимый |
| `8` | 8 | `process_id` | Атрибутированный PID или `0`, когда его невозможно определить |
| `16` | 8 | `tid` | Захваченный ID потока Windows (`u64`) или `0`, когда он недоступен |
| `24` | 4 | `compartment_id` | ID сетевого компартмента WFP (`u32`) или `0`, когда он недоступен |
| `28` | 4 | `condition_flags` | Необработанная битовая маска `FWP_CONDITION_FLAG_*` (`u32`) из этой индикации WFP |
| `32` | 4 | `interface_index` | Индекс интерфейса для индикации WFP (`u32`) |
| `36` | 4 | `sub_interface_index` | Индекс подинтерфейса для индикации WFP (`u32`) |
| `40` | 1 | `direction` | Направление пакета, по которому принимается решение |
| `41` | 1 | `protocol` | Номер IP-протокола |
| `42` | 4 | `local_ip` | Локальный адрес IPv4 |
| `46` | 4 | `remote_ip` | Удалённый адрес IPv4 |
| `50` | 2 | `local_port` | Локальный порт или `0` для протокола без портов |
| `52` | 2 | `remote_port` | Удалённый порт или `0` для протокола без портов |
| `54` | 1 | `payload_layer` | Уровень, представленный захваченными байтами |
| `55` | 4 | `captured_length` | Число следующих байтов |
| `59` | N | `captured_bytes` | Захваченные байты пакета |

Допустимая длина полезной нагрузки — `59 + captured_length`. Полная обрамлённая запись имеет размер `5 + 59 + captured_length` байтов.

### `ConnectionIpv6` (`info_type = 8`)

Фиксированная полезная нагрузка составляет 83 байта. Префикс метаданных и его смещения идентичны IPv4; более крупные адреса сдвигают следующие поля:

| Смещение | Размер | Поле | Описание |
|---:|---:|---|---|
| `0` | 8 | `id` | ID запроса для команды `Verdict` |
| `8` | 8 | `process_id` | Атрибутированный PID или `0`, когда он неизвестен |
| `16` | 8 | `tid` | Захваченный ID потока Windows (`u64`) или `0`, когда он недоступен |
| `24` | 4 | `compartment_id` | ID сетевого компартмента WFP (`u32`) или `0`, когда он недоступен |
| `28` | 4 | `condition_flags` | Необработанная битовая маска `FWP_CONDITION_FLAG_*` (`u32`) из этой индикации WFP |
| `32` | 4 | `interface_index` | Индекс интерфейса для индикации WFP (`u32`) |
| `36` | 4 | `sub_interface_index` | Индекс подинтерфейса для индикации WFP (`u32`) |
| `40` | 1 | `direction` | Направление пакета, по которому принимается решение |
| `41` | 1 | `protocol` | Номер IP-протокола |
| `42` | 16 | `local_ip` | Локальный адрес IPv6 |
| `58` | 16 | `remote_ip` | Удалённый адрес IPv6 |
| `74` | 2 | `local_port` | Локальный порт или `0` |
| `76` | 2 | `remote_port` | Удалённый порт или `0` |
| `78` | 1 | `payload_layer` | Уровень, представленный захваченными байтами |
| `79` | 4 | `captured_length` | Число следующих байтов |
| `83` | N | `captured_bytes` | Захваченные байты пакета |

Допустимая длина полезной нагрузки — `83 + captured_length`. Полная обрамлённая запись имеет размер `5 + 83 + captured_length` байтов.

#### Семантика полей события подключения

`direction`:

| Значение | Имя | Значение |
|---:|---|---|
| `0` | `Outbound` | Пакет передаётся от локальной конечной точки наружу |
| `1` | `Inbound` | Пакет передаётся к локальной конечной точке |

В событии подключения это эффективное направление пакета, по которому принимается решение. В событии завершения подключения это направление подключения, сохранённое при регистрации этого подключения.

`payload_layer`:

| Значение | Уровень | Содержимое `captured_bytes` |
|---:|---|---|
| `3` | Сеть | Байты, начинающиеся с IP-заголовка |
| `4` | Транспорт/ALE | Байты транспортного уровня; первоначальное исходящее TCP-подключение обычно не имеет захваченной полезной нагрузки |

Событие подключения является запросом решения, а не гарантией одного события на логическое подключение. Пока решение временное или подключение остаётся `Undecided`, несколько пакетов с одним пятиэлементным кортежем могут получать разные ID. Индикация WFP, содержащая несколько объектов `NET_BUFFER`, разделяется на одно событие и один ID запроса для каждого пакета. Каждый ненулевой ID должен получить ровно один `Verdict`, даже если UI или фильтр отображения скрывает событие.

`tid` включён непосредственно в каждое событие подключения версии 3. Для запросов, связанных с подключением, при публикации снимается TID из точного действующего поколения кэша. При атрибуции исходящих TCP/UDP ALE TID захватывается только если PID не является ни неизвестным/System (`0` или `4`), ни контроллером, которому принадлежит дескриптор драйвера; также применяется существующая атрибуция исходящего контекста выполнения и ICMP echo. Недоступный TID имеет значение `0`. Значение атрибутируется наблюдаемому запросу или подключению и не обязательно является потоком, отправившим каждый последующий пакет. Это не поток чтения монитора. Запрос IOCTL не требуется, а потребление или удаление запроса не делает недействительными метаданные, уже переданные его событием.

`condition_flags` является полной, неизменённой 32-битной маской `FWP_CONDITION_FLAG_*` из поля `Flags` текущего уровня классификации (авторизация ALE или входящий/исходящий IP-пакет). Биты не синтезируются из адресов и не копируются из более раннего события подключения. Например, `FWP_CONDITION_FLAG_IS_LOOPBACK` равен `0x00000001`, а `FWP_CONDITION_FLAG_IS_REAUTHORIZE` равен `0x00000004`; применимые биты зависят от уровня. Неизвестные биты сохраняются. Отсутствующее поле или поле, не являющееся `FWP_UINT32`, кодируется как `0`, что неотличимо от нативной нулевой маски.

`compartment_id`, `interface_index` и `sub_interface_index` описывают текущую индикацию WFP, а не неизменяемый маршрут подключения. Они копируются из данных классификации ALE или снимка маршрутизации уровня пакета. Недоступные значения кодируются как `0`; индексы интерфейса и подинтерфейса могут правомерно быть нулевыми на уровнях ALE. У формата нет маски присутствия, поэтому нативный ноль и недоступные метаданные невозможно различить.

Клиент C++ предоставляет эти поля как `Connection::tid`, `Connection::compartment_id`, `Connection::condition_flags`, `Connection::interface_index` и `Connection::sub_interface_index`. `kext_monitor` выводит `tid` в заголовке `CONN` и метаданные маршрутизации с `condition_flags=0x%08x` в отдельной строке. Метаданные переносятся событием независимо от фильтров отображения, отложенных вердиктов или `--no-verdicts`. Записи завершения подключения не включают эти пять полей и сохраняют свой существующий формат.

Успешный `WriteFile` для вердикта означает, что драйвер принял команду; он не подтверждает доставку повторно инъецированного пакета. Инъекция WFP завершается асинхронно, и окончательная ошибка инъекции записывается в кольцо журнала драйвера. Независимые повторные инъекции UDP не образуют контракт FIFO, поэтому этот API не гарантирует порядок доставки разрешённых UDP-датаграмм.

Заголовок полезной нагрузки идентичен. Каждая запись IPv6 имеет размер 52 байта:

| Смещение внутри записи | Размер | Поле |
|---:|---:|---|
| `0` | 16 | `local_ip` |
| `16` | 2 | `local_port` |
| `18` | 16 | `remote_ip` |

| `44` | 8 | `received_bytes` |

Общая длина полезной нагрузки составляет `5 + entry_count * 52`.

Одна команда `GetBandwidthStats` может поставить в очередь до четырёх записей: TCPv4, TCPv6, UDPv4 и UDPv6. Пустые наборы не выдаются. Каждый запрос атомарно забирает текущие карты, поэтому значения представляют байты, накопленные с предыдущего запроса:

- Счётчики TCP содержат длины данных потока;
- Счётчики UDP содержат длины полезной нагрузки датаграмм, исключая заголовок UDP;
- `transmitted_bytes` — исходящий трафик;
- `received_bytes` — входящий трафик.

Записи пропускной способности не содержат PID.

## Запись команд с помощью `WriteFile`

Каждая команда начинается с однобайтового `command_type`. Общего поля длины нет, поскольку каждый тип команды имеет фиксированный размер полезной нагрузки.

Один вызов `WriteFile` может содержать несколько полных команд, последовательно объединённых. Команду нельзя разделить между отдельными вызовами `WriteFile`: неполная полезная нагрузка недопустима. Пустая запись, неизвестный тип или усечённая команда завершаются с `STATUS_INVALID_PARAMETER`.

Команды применяются в порядке следования в буфере. Если более поздняя команда в том же буфере недопустима, все предшествующие команды уже вступили в силу, а `IoStatus.Information` содержит смещение в байтах недопустимой команды. При полном успехе потреблённая длина равна полной длине входного буфера.

| `command_type` | Имя | Полезная нагрузка | Общий размер |
|---:|---|---:|---:|
| `0` | `Shutdown` | Нет | 1 |
| `1` | `Verdict` | 9 байт | 10 |
| `2` | `UpdateV4` | 14 байт | 15 |
| `3` | `UpdateV6` | 38 байт | 39 |
| `4` | `ClearCache` | Нет | 1 |
| `5` | `GetLogs` | Нет | 1 |
| `6` | `GetBandwidthStats` | Нет | 1 |
| `7` | `PrintMemoryStats` | Нет | 1 |
| `8` | `CleanEndedConnections` | Нет | 1 |

### `Shutdown` (`command_type = 0`)

У этой команды нет полезной нагрузки, и она выполняет ту же операцию завершения работы, что и `IOCTL_SHUTDOWN_REQUEST`:

- закрывает допуск для новых классификаций WFP;
- разблокирует ожидающее чтение;
- принимает решение об отказе для каждого пакета, всё ещё ожидающего вердикта;
- очищает состояние конечных точек, необходимое для корректной выгрузки.

Это заключительная команда для текущего экземпляра драйвера. Она не выгружает саму службу. После её завершения клиент должен дождаться завершения чтения, закрыть дескриптор устройства и только затем остановить службу. Повторное использование сеанса после `Shutdown` не поддерживается.

### `Verdict` (`command_type = 1`)

Полезная нагрузка:

| Смещение | Размер | Поле |
|---:|---:|---|
| `0` | 8 | `id` (`u64 LE`) |
| `8` | 1 | `verdict` |

`id` должен идентифицировать всё ещё ожидающее событие `ConnectionIpv4` или `ConnectionIpv6`. Неизвестный или уже использованный ID не приводит к ошибке `WriteFile`: команда успешно завершается, но драйвер записывает `Verdict invalid id` в своё кольцо журнала. Недопустимое числовое значение `verdict` завершается с `STATUS_INVALID_PARAMETER` и не потребляет ожидающий пакет.

| Значение | Имя | Семантика |
|---:|---|---|
| `0` | `Undecided` | Внутреннее начальное состояние; в качестве ответа не допускает текущий пакет и оставляет соединение требующим более поздних решений |
| `1` | `Undeterminable` | Блокирует без новых запросов, пока существует экземпляр кэша |
| `2` | `Accept` | Допускает только текущий удерживаемый пакет; для последующих пакетов требуется другое решение |
| `3` | `PermanentAccept` | Допускает текущий и последующие пакеты для этого экземпляра кэша |
| `4` | `Block` | Блокирует текущий пакет; решение временное, и последующий пакет может создать другой запрос |
| `5` | `PermanentBlock` | Жёстко блокирует текущий и последующие пакеты для этого экземпляра кэша |
| `6` | `Drop` | Без уведомления поглощает текущий пакет; решение временное |
| `7` | `PermanentDrop` | Без уведомления поглощает последующие пакеты для этого экземпляра кэша |
| `10` | `Failed` | Блокирует, представляя постоянный сбой принятия решения по политике |

Значения `8`, `9` и `11` зарезервированы и отклоняются с `STATUS_INVALID_PARAMETER`
командами `Verdict`, `UpdateV4` и `UpdateV6`. Остальные значения вердиктов остаются неизменными,
включая `Failed = 10`. Драйвер не поддерживает перенаправление трафика.

Для пакета без состояния, не имеющего экземпляра соединения, например некоторого трафика ICMP или внешне инжектированного трафика, наблюдаемого после закрытия исходной конечной точки, вердикт применяется только к указанному ID запроса. Даже `PermanentAccept` не создаёт постоянную запись для последующих пакетов без состояния.

### `UpdateV4` (`command_type = 2`)

Изменяет вердикт существующего активного IPv4-соединения, выбранного по его точному пятиэлементному кортежу:

| Смещение | Размер | Поле |
|---:|---:|---|
| `0` | 1 | `protocol` |
| `1` | 4 | `local_address` |
| `5` | 2 | `local_port` |
| `7` | 4 | `remote_address` |
| `11` | 2 | `remote_port` |
| `13` | 1 | `verdict` |

### `UpdateV6` (`command_type = 3`)

| Смещение | Размер | Поле |
|---:|---:|---|
| `0` | 1 | `protocol` |
| `1` | 16 | `local_address` |
| `17` | 2 | `local_port` |
| `19` | 16 | `remote_address` |
| `35` | 2 | `remote_port` |
| `37` | 1 | `verdict` |

Обе команды обновления:

- принимают те же значения вердикта, что и `Verdict`;
- обновляют только текущую активную запись и никогда не изменяют сохранённую историю завершённых соединений;
- успешно завершаются без каких-либо действий, если совпадающего кортежа не существует;
- не отвечают на ожидающий ID запроса;
- сбрасывают фильтры ALE, для которых поддерживается сброс, чтобы существующий поток был повторно авторизован в соответствии с новой политикой.

Событие ответа или отдельное указание того, что кортеж был найден, отсутствуют.

### `ClearCache` (`command_type = 4`)

Очищает кэши IPv4- и IPv6-соединений, а также кэши конечных точек TCP и UDP, согласовывает оставшееся состояние жизненного цикла UDP и сбрасывает фильтры ALE, для которых поддерживается сброс. Не выдаёт события `ConnectionEnd` для удалённых записей.

`ClearCache` не очищает ожидающие ID запросов, карты пропускной способности, кэш эхо-сообщений ICMP или кольцо журнала. Клиент всё ещё может получить ID запросов, опубликованные до очистки. Запоздалый вердикт нельзя применить к новому соединению, повторно использовавшему старый кортеж.

### `GetLogs` (`command_type = 5`)

Извлекает все накопленные на данный момент сообщения из кольца журнала и ставит в очередь их записи `LogLine`. Доставка асинхронна через `ReadFile`, без маркера конца списка. Сообщения, записанные после снимка, остаются в кольце до следующего запроса `GetLogs`.

### `GetBandwidthStats` (`command_type = 6`)

Извлекает накопленные карты TCP/UDP и ставит в очередь непустые записи `BandwidthStatsV4` и `BandwidthStatsV6`. Маркера конца ответа нет, а записи пропускной способности могут перемежаться с событиями соединений и журнала.

### `PrintMemoryStats` (`command_type = 7`)

Сначала выполняет ограниченное обслуживание состояния неустановленных TCP-соединений, затем записывает диагностические размеры в кольцо журнала для:

- кэша ожидающих пакетов;
- кэшей IPv4- и IPv6-соединений;
- неотслеживаемых записей кэша соединений;
- всех четырёх карт пропускной способности;
- кэша конечных точек TCP и ожидающих закрытий;
- конечных точек и одноранговых узлов UDP;
- регистраций потоков UDP и обратных вызовов;
- кэша эхо-сообщений ICMP.

Статистика создаётся в виде строк журнала и сама по себе не попадает в выходной поток. После этого отправьте `GetLogs`, чтобы получить её. Обе команды можно отправить в одной записи как байты `[7, 5]`.

### `CleanEndedConnections` (`command_type = 8`)

Выполняет периодическое обслуживание состояния:

- удаляет историю завершённых соединений по истечении её 60-секундного льготного периода;
- завершает неотслеживаемые резервные соединения пакетного уровня, включая эвристические входящие записи UDP, созданные `EnableInboundUdpCacheMissPidFallback`, после 60 секунд бездействия и выдаёт события их завершения;
- завершает локальные авторизации TCP, которые не достигли `FLOW_ESTABLISHED` в течение 10 секунд;
- согласовывает устаревшие регистрации конечных точек и потоков UDP;
- удаляет истёкшие сопоставления эхо-сообщений ICMP.

Клиент пользовательского режима отвечает за периодическую отправку этой команды. Драйвер не выполняет этот периодический обход самостоятельно.

## API IOCTL

Все управляющие коды используют:

```text
CTL_CODE(40000, function, METHOD_BUFFERED, FILE_READ_DATA | FILE_WRITE_DATA)
```

Поэтому дескриптор устройства должен иметь доступ и на чтение, и на запись.

| Код | Числовое значение | Вход | Выход | Описание |
|---|---:|---:|---:|---|
| `IOCTL_VERSION` | `0x9C40E000` | Нет | Ровно 4 байта | Версия интерфейса протокола |
| `IOCTL_SHUTDOWN_REQUEST` | `0x9C40E004` | Нет | Нет | Окончательное завершение работы драйвера |

### `IOCTL_VERSION`

Возвращает четыре необработанных байта, хранящиеся в [windows_kext/kextinterface/version.txt](windows_kext/kextinterface/version.txt). Текущая версия — `[3, 0, 0, 0]`, обычно отображаемая как **3.0.0.0**; возвращаемые байты — `03 00 00 00`. Эта версия требует описанных выше ID и компоновок событий соединений и несовместима с исходным расширением ядра Portmaster для Windows. Если выходной буфер короче четырёх байт, запрос завершается с `STATUS_BUFFER_TOO_SMALL` и не возвращает частичного результата.

### `IOCTL_SHUTDOWN_REQUEST`

Выполняет ту же операцию, что и команда `Shutdown`. IOCTL позволяет удобно отправить заключительный запрос вне основного потока команд, пока ожидается завершение асинхронного чтения. Выходных данных нет.

Бывший `IOCTL_GET_THREAD_ID` (`0x9C40E008`, функция `0x802`) не поддерживается в версии 3. Его поиск для каждого запроса удалён; вместо этого используйте поле `tid` в событии соединения. Вызов этого удалённого IOCTL, как и любого другого неизвестного IOCTL, завершается с `STATUS_NOT_IMPLEMENTED`.

## Рекомендуемый жизненный цикл клиента

1. Настройте любые [параметры реестра](#registry-settings) до запуска службы драйвера ядра либо используйте уже установленный релизный драйвер.
2. Откройте `\\.\PortmasterKext` с `GENERIC_READ | GENERIC_WRITE`, режимом общего доступа `0` и `FILE_FLAG_OVERLAPPED`.
3. Проверьте `IOCTL_VERSION` и убедитесь, что клиент поддерживает возвращённую версию до начала обмена по протоколу; версия 3 требует значений `info_type` `7`/`8` и расширенных компоновок событий соединений.
4. Запустите одно постоянно активное асинхронное чтение и собирайте записи независимо от границ чтения.
5. Получайте TID и метаданные маршрутизации непосредственно из каждого события соединения. На каждый ненулевой ID запроса соединения отвечайте вердиктом; IOCTL для метаданных не требуется. Фильтры отображения не должны подавлять вердикты.
6. Периодически отправляйте `CleanEndedConnections` и по необходимости запрашивайте журналы или статистику пропускной способности.
7. Для завершения выполните `IOCTL_SHUTDOWN_REQUEST` или команду `Shutdown`.
8. Дождитесь завершения ожидающего чтения и получите его результат, затем закройте дескриптор устройства.
9. Останавливайте службу только после закрытия дескриптора. Драйвер без PnP не может завершить выгрузку, пока его управляющее устройство остаётся открытым.

Не следует принудительно завершать контроллер с открытым дескриптором, рассчитывая, что затем завершится `sc stop`: служба может остаться в состоянии `STOP_PENDING`.

## API C++ (`kext_client`)

Заголовочный файл [kext_client/include/PortmasterKext.h](kext_client/include/PortmasterKext.h) предоставляет пространство имён `pmkext` и декодированные структуры `Connection`, `ConnectionEnd`, `LogLine`, `BandwidthEntry` и `BandwidthStats`.

Помимо `process_id`, каждое декодированное `Connection` предоставляет метаданные версии 3:

| Поле | Тип C++ | Значение |
|---|---|---|
| `tid` | `uint64_t` | Захваченный ID потока Windows или `0`, если недоступен |
| `compartment_id` | `uint32_t` | ID сетевого отсека WFP или `0`, если недоступен |
| `interface_index` | `uint32_t` | Индекс интерфейса для текущей индикации WFP |
| `sub_interface_index` | `uint32_t` | Индекс подинтерфейса для текущей индикации WFP |

Считывайте эти члены в `on_connection`; в этом API нет метода `Driver::GetThreadId`. Декодер принимает события соединений с типами `7`/`8` и предупреждает об устаревших типах `1`/`2`. Это декодированные объекты C++, а не упакованные структуры проводного формата; используйте приведённые выше компоновки проводного формата вместо копирования байтов `sizeof(Connection)` в устройство или из него. Сведения о выводе монитора и использовании клиента см. в [kext_client/README.md](kext_client/README.md#connection-metadata).

### `pmkext::Driver`

| Метод | Назначение |
|---|---|
| `Driver(service_name)` | Создаёт контроллер; имя по умолчанию — `PortmasterKext` |
| `Install(sys_path, error, inbound_udp_pid_fallback = true)` | Создаёт и запускает службу ядра с запуском по требованию, используя абсолютный путь; записывает `EnableInboundUdpCacheMissPidFallback` из необязательного аргумента; существующая служба считается конфликтом |
| `Open(error)` | Открывает дескриптор устройства для асинхронного ввода-вывода и запускает сервер моста именованного канала |
| `Run(handlers, poll_interval_ms)` | Читает и диспетчеризует события до `Stop`; вызывает `on_poll` с запрошенным интервалом |
| `Stop()` | Подаёт сигнал `Run` и однократно отправляет IOCTL завершения работы |
| `GetVersion(out, error)` | Вызывает `IOCTL_VERSION` |
| `RequestShutdown(error)` | Вызывает `IOCTL_SHUTDOWN_REQUEST` |
| `SendVerdict(id, verdict, error)` | Кодирует и отправляет команду `Verdict` |
| `RequestLogs(error)` | Отправляет `GetLogs` |
| `RequestBandwidthStats(error)` | Отправляет `GetBandwidthStats` |
| `RequestMemoryStats(error)` | Отправляет `PrintMemoryStats` |
| `RequestCleanEndedConnections(error)` | Отправляет команду периодического обслуживания |
| `RequestClearCache(error)` | Отправляет `ClearCache` |
| `Cleanup()` | Закрывает дескриптор, останавливает только службу, запущенную этим объектом, и удаляет только службу, созданную этим объектом |

`Driver` не копируется, а его деструктор вызывает `Cleanup()`.

`Handlers` содержит необязательные обратные вызовы:

- `on_connection(const Connection&)`;
- `on_connection_end(const ConnectionEnd&)`;
- `on_log(const LogLine&)`;
- `on_bandwidth(const BandwidthStats&)`;
- `on_warning(const std::string&)` для предупреждений декодирования и протокола;
- `on_poll()` для периодических команд.

Обратные вызовы событий выполняются в потоке чтения, тогда как `on_poll` выполняется в потоке, вызвавшем `Run`. Когда клиент именованного канала подключён к мосту, полные необработанные записи драйвера пересылаются этому клиенту вместо передачи локальным обратным вызовам событий. Тогда подключённый клиент отвечает за возврат вердиктов.

Класс C++ в настоящее время не предоставляет методов для `UpdateV4` или `UpdateV6`; эти команды остаются доступными через необработанный протокол драйвера. Входящая в комплект эталонная реализация Go по-прежнему использует устаревшие ID и компоновки событий соединений, поэтому её необходимо перенести, прежде чем она сможет служить контроллером версии 3.

Вспомогательные функции `ToString`, `PayloadLayerToString`, `ProtocolToString`, `DirectionToString`, `FormatIpv4` и `FormatIpv6` форматируют только уже декодированные значения.

## Сборка и тестирование

### Поддерживаемая конфигурация и меры предосторожности

Эта процедура сборки и запуска документирована **только для Windows 11 Enterprise 26H2, x64**, с **включённой UEFI Secure Boot** и вручную активированной политикой **`CodeIntegrity-AllowConfigurablePolicy-CustomKernelSigners`**. В ней используются пользовательский UEFI Platform Key (PK), подписанная политика Code Integrity и локально выданный сертификат подписи в режиме ядра. Это не процедура подписи Microsoft/WHQL и она не устанавливает совместимость с другими выпусками или редакциями Windows.

Драйвер поддерживает **только релизные сборки**. Отладочная сборка намеренно завершается ошибкой во время компиляции. Цель фиксирована как `x86_64-pc-windows-msvc` с `panic=abort`.

> **Перед изменением системы:** используйте машину для разработки/тестов, которой вы управляете, с доступом к локальной консоли и проверенным USB-носителем для восстановления. Создайте резервные копии Windows, существующей политики EFI и ключей/баз данных Secure Boot прошивки (PK, KEK, db и dbx) либо обеспечьте поддерживаемый поставщиком способ их восстановления. Сохраните ключ восстановления BitLocker/шифрования устройства вне машины и приостановите защиту для запланированных изменений прошивки/загрузки в соответствии с вашей процедурой восстановления. Некорректная принудительно применяемая политика или отсутствующий сертификат загрузчика могут помешать запуску Windows. Подписанная политика защищена от несанкционированного изменения; удаление её файла не является общей процедурой отката. Перед развёртыванием ознакомьтесь с [мерами предосторожности Microsoft для подписанных политик](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/deployment/use-signed-policies-to-protect-appcontrol-against-tampering).

**Проверьте поддержку ОС, прежде чем что-либо развёртывать:** существующее значение `REG_DWORD` `CustomKernelSignerLockedEnabled` должно присутствовать в разделе `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\CI\Protected`. Если его нет, установите текущие обновления Windows для Windows 11 Enterprise 26H2, перезагрузитесь и проверьте снова **до копирования принудительно применяемой политики в EFI**. Не создавайте значение вручную в качестве замены отсутствующей поддержки ОС. Если оно по-прежнему отсутствует, прекратите эту процедуру.

Установите [предварительные требования для сборки](#build-prerequisites) перед началом: `signtool.exe` из Windows SDK уже требуется на шаге 2. В примерах предполагается, что рабочая копия находится в `C:\portmaster_v3`, а Windows установлена в `C:\Windows`.

Используйте **64-битный Windows PowerShell 5.1 от имени администратора** для приведённых ниже команд работы с сертификатами, ConfigCI, EFI и проверки. Команды Windows PowerShell/ConfigCI не являются командами Git Bash; не используйте PowerShell 7 вместо Windows PowerShell 5.1 для этой процедуры. При любой ошибке останавливайтесь, а не продолжайте с неполными результатами.

### 1. Создайте локальные сертификаты

Перейдите в `windows_kext`; все относительные пути вывода в шагах 1 и 2 относятся к этому каталогу:

```powershell
Set-Location 'C:\portmaster_v3\windows_kext'
```

Запустите следующий сценарий генерации сертификатов. Он создаёт самоподписанный корневой CA и два сертификата, выданных этим CA, с экспортируемыми закрытыми ключами в `Cert:\LocalMachine\My`, затем экспортирует их в текущий каталог:

```powershell
$pwd = ConvertTo-SecureString -String "1" -Force -AsPlainText

$cert_params = @{
    Type = 'Custom'
    Subject = 'CN=Localhost Root Certification Authority'
    FriendlyName = 'Localhost Root Certification Authority'
    TextExtension = '2.5.29.19={text}CA=1'
    HashAlgorithm = 'sha512'
    KeyLength = 4096
    KeyAlgorithm = 'RSA'
    KeyUsage = 'CertSign','CRLSign'
    KeyExportPolicy = 'Exportable'
    NotAfter = (Get-Date).AddYears(100)
    CertStoreLocation = 'Cert:\LocalMachine\My'
}

$root_cert = New-SelfSignedCertificate @cert_params

Export-PfxCertificate -Cert $root_cert -FilePath ./localhost-root-ca.pfx -Password $pwd
Export-Certificate -Cert $root_cert -FilePath ./localhost-root-ca.der


$cert_params = @{
    Type = 'Custom'
    Subject = 'CN=Localhost UEFI Platform Key Certificate'
    FriendlyName = 'Localhost UEFI Platform Key Certificate'
    TextExtension = '2.5.29.19={text}CA=0'
    Signer = $root_cert
    HashAlgorithm = 'sha256'
    KeyLength = 2048
    KeyAlgorithm = 'RSA'
    KeyUsage = 'DigitalSignature'
    KeyExportPolicy = 'Exportable'
    NotAfter = (Get-Date).AddYears(10)
    CertStoreLocation = 'Cert:\LocalMachine\My'
}

$pk_cert = New-SelfSignedCertificate @cert_params

Export-PfxCertificate -Cert $pk_cert -FilePath ./localhost-pk.pfx -Password $pwd
Export-Certificate -Cert $pk_cert -FilePath ./localhost-pk.der


$cert_params = @{
    Type = 'CodeSigningCert'
    Subject = 'CN=Localhost Kernel Mode Driver Certificate'
    FriendlyName = 'Localhost Kernel Mode Driver Certificate'
    TextExtension = '2.5.29.19={text}CA=0'
    Signer = $root_cert
    HashAlgorithm = 'sha256'
    KeyLength = 2048
    KeyAlgorithm = 'RSA'
    KeyUsage = 'DigitalSignature'
    KeyExportPolicy = 'Exportable'
    NotAfter = (Get-Date).AddYears(10)
    CertStoreLocation = 'Cert:\LocalMachine\My'
}

$km_cert = New-SelfSignedCertificate @cert_params

Export-PfxCertificate -Cert $km_cert -FilePath ./localhost-km.pfx -Password $pwd
Export-Certificate -Cert $km_cert -FilePath ./localhost-km.der
```

| Пара файлов (`.pfx` / `.der`) | Назначение |
|---|---|
| `localhost-root-ca` | Корневой CA, выдающий сертификаты PK и KM; его открытый сертификат образует цепочку подписи драйвера |
| `localhost-pk` | Подписывает `SiPolicy.bin`; его открытый сертификат регистрируется как UEFI **PK** |
| `localhost-km` | Подписывает драйвер; его открытый сертификат авторизован политикой Code Integrity для кода **в режиме ядра** |

Файлы `.der` содержат открытые сертификаты; файлы `.pfx` также содержат **закрытые ключи**. Не коммитьте PFX-файлы и не публикуйте их вместе с артефактами сборки. Храните защищённые резервные копии, особенно закрытых ключей root и PK: они управляют выдачей сертификатов и будущими обновлениями политики. Не создавайте сертификаты заново после регистрации PK/развёртывания политики, если только вы также не планируете соответствующую миграцию политики доверия.

> Поставляемый сценарий использует пример пароля PFX **`1`**, соответствующий приведённым ниже примерам подписи. Это небезопасный пароль для реального хранения ключей. Если вы измените его, также обновите команду подписи политики и пароль PFX, используемый `windows_kext\link-dev.ps1`.

### 2. Создайте и подпишите `SiPolicy.p7b`

Продолжайте в том же сеансе Windows PowerShell с повышенными правами и в каталоге `windows_kext`. Создайте политику Code Integrity в формате единой политики из корней подписи установленной системы, авторизуйте обновления политики, подписанные PK, и добавьте сертификат KM как подписывающий в режиме ядра:

```powershell
New-CIPolicy -FilePath .\SiPolicy.xml -Level RootCertificate -ScanPath C:\Windows\System32\
Set-RuleOption -FilePath .\SiPolicy.xml -Option 3 -Delete
Set-RuleOption -FilePath .\SiPolicy.xml -Option 6 -Delete
Add-SignerRule -FilePath .\SiPolicy.xml -CertificatePath .\localhost-pk.der -Update
Add-SignerRule -FilePath .\SiPolicy.xml -CertificatePath .\localhost-km.der -Kernel
ConvertFrom-CIPolicy -XmlFilePath .\SiPolicy.xml -BinaryFilePath .\SiPolicy.bin
```

- Удаление параметра **3** (`Enabled:Audit Mode`) делает политику **принудительно применяемой**, а не только для аудита.
- Удаление параметра **6** (`Enabled:Unsigned System Integrity Policy`) требует подписанных обновлений политики.
- `-Update` авторизует сертификат PK для подписи обновлений политики; он не авторизует этот сертификат для подписи драйверов. `-Kernel` авторизует сертификат KM для кода в режиме ядра.
- Правила `RootCertificate` доверяют корням подписи, а не только отдельным отсканированным файлам. И наоборот, сканирование `System32` может не обнаружить необходимые сторонние драйверы, хранящиеся в другом месте. Перед принудительным применением просмотрите предупреждения сканирования и охват политики, включая загрузочные драйверы и драйверы хранения. Не развёртывайте неполную политику.

Подпишите двоичную политику закрытым ключом PK. Приведённый полный путь SDK предполагает Windows SDK **10.0.28000.0**; если установлена другая версия, используйте её фактический путь `x64\signtool.exe`:

```powershell
& 'C:\Program Files (x86)\Windows Kits\10\bin\10.0.28000.0\x64\signtool.exe' sign /fd sha256 /p7co 1.3.6.1.4.1.311.79.1 /p7 . /f .\localhost-pk.pfx /p 1 /n "Localhost UEFI Platform Key Certificate" .\SiPolicy.bin
```

Только после успешного выполнения SignTool и создания `SiPolicy.bin.p7` переименуйте этот **подписанный результат**, а не неподписанный файл `.bin`:

```powershell
Move-Item -LiteralPath .\SiPolicy.bin.p7 -Destination .\SiPolicy.p7b
```

Сохраните `SiPolicy.xml`, сертификаты и подписанную политику для восстановления и будущих обновлений. Эти шаги описывают первоначальное развёртывание: не перезаписывайте существующую подписанную политику без запланированного обновления, подписанного авторизованным подписывающим обновления.

### 3. Скопируйте подписанную политику в системный раздел EFI

Используйте свободную букву диска (`X:` в этом примере) и подключите системный раздел EFI настраиваемой установки Windows:

```powershell
mountvol.exe X: /S
```

Если `X:\EFI\Microsoft\Boot\SiPolicy.p7b` уже существует, **остановитесь и создайте его резервную копию**, прежде чем планировать замену. На машине с несколькими загрузками/дисками убедитесь, что это правильный раздел EFI. Для нового развёртывания скопируйте подписанный файл:

```powershell
Copy-Item -LiteralPath .\SiPolicy.p7b -Destination 'X:\EFI\Microsoft\Boot\SiPolicy.p7b'
```

Удалите временное подключение с буквой диска:

```powershell
mountvol.exe X: /D
```

Выполните указанные ниже изменения автономного реестра и прошивки **до следующего запуска целевой установки Windows**.

### 4. Включите `CustomKernelSigners` в автономном кусте SYSTEM

Требуемое значение в целевой установке Windows:

```text
Раздел:   HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\CI\Protected
Параметр: CustomKernelSignerLockedEnabled
Тип:      REG_DWORD
Данные:   1
```

Значение уже должно существовать, как было проверено перед развёртыванием политики. Не создавайте его вручную, если оно отсутствует; необходимые обновления Windows должны быть установлены до начала этой процедуры.

Это защищённое значение нельзя изменить из работающей целевой системы. Не изменяйте владельца/разрешения раздела `CI\Protected` действующей системы. Вместо этого загрузите куст реестра целевой системы из другой установки Windows или доверенной среды Windows PE/live USB:

1. Полностью выключите целевую установку Windows; не оставляйте её в гибернации и не используйте выключение с быстрым запуском. Загрузите другую среду Windows/Windows PE. Заранее убедитесь, что носитель восстановления может загрузиться с предполагаемой конфигурацией Secure Boot.
2. Найдите том целевой Windows. Его буква диска может отличаться от обычной; в примере ниже используется **`D:\Windows`**. Если BitLocker включён, разблокируйте этот том его ключом восстановления. Создайте резервную копию `D:\Windows\System32\Config\SYSTEM` и связанных с ним журналов транзакций до редактирования.
3. Запустите **Редактор реестра (`regedit.exe`) от имени администратора** в среде восстановления. Выберите **`HKEY_LOCAL_MACHINE`**, затем **Файл → Загрузить куст**. Откройте **`D:\Windows\System32\Config\SYSTEM`** и задайте ему временное имя **`OfflineSYSTEM`**. Не редактируйте собственный куст SYSTEM среды восстановления.
4. Откройте **`HKEY_LOCAL_MACHINE\OfflineSYSTEM\Select`** и проверьте значения DWORD **`Current`** и **`Default`**. `Current` определяет последний активный набор управления; `Default` выбирает набор управления для следующего обычного запуска. Обычно оба равны `1`, что означает **`ControlSet001`**. При `Default = 2` используйте `ControlSet002` и так далее. Не считайте `ControlSet001` без проверки. В автономном кусте нет активного псевдонима `CurrentControlSet`.
5. В наборе управления, выбранном для следующего обычного запуска, откройте **`Control\CI\Protected`**. При `Default = 1` полный автономный путь:

   ```text
   HKEY_LOCAL_MACHINE\OfflineSYSTEM\ControlSet001\Control\CI\Protected
   ```

   Дважды щёлкните существующее значение **`CustomKernelSignerLockedEnabled`**, подтвердите, что это **`REG_DWORD`**, и задайте **Данные значения** как **`1`**. Десятичная и шестнадцатеричная записи эквивалентны для этого значения. Если значение отсутствует, не создавайте его; вернитесь к проверке обновлений Windows/поддержки выше.
6. Выберите **`HKEY_LOCAL_MACHINE\OfflineSYSTEM`**, затем **Файл → Выгрузить куст** и подтвердите. Это сохраняет изменения и освобождает куст. Закройте Редактор реестра и выключите среду восстановления.

### 5. Зарегистрируйте пользовательский PK и проверьте Secure Boot

Скопируйте открытый сертификат **`localhost-pk.der`** на USB-накопитель, читаемый прошивкой (обычно FAT32). Не помещайте PFX/закрытые ключи на этот накопитель. Войдите в настройки UEFI/BIOS машины:

1. Переключите управление ключами Secure Boot из **Standard Mode** в **Custom Mode**. Точные названия меню и процедура регистрации зависят от поставщика прошивки.
2. В управлении **Platform Key (PK)** замените/зарегистрируйте PK с помощью **`localhost-pk.der`**, того же сертификата, закрытый ключ которого подписал `SiPolicy.p7b`. Регистрация этого пользовательского PK **обязательна для описанной здесь процедуры подписи драйвера**, независимо от версии прошивки. Этот сертификат должен находиться в **PK**, а не в db или KEK. Сертификат драйвера KM авторизован политикой CI и не требует регистрации в качестве PK прошивки.
3. Сохраните существующие записи **KEK, db и dbx**, необходимые для загрузки Windows и сохранения сведений об отозванных сертификатах. Не используйте общую операцию **Clear all Secure Boot keys**. Убедитесь, что db доверяет цепочке сертификатов установленного диспетчера загрузки Windows.
4. Перед загрузкой Windows проверьте сертификаты Microsoft в KEK и db и при необходимости добавьте описанные ниже сертификаты.
5. Оставьте **Secure Boot включённой и активной**, сохраните настройки прошивки и загрузите настроенную установку Windows. **Custom Mode не равнозначен отключению Secure Boot**; машина не должна оставаться в Setup Mode без зарегистрированного PK.

**Обновления сертификатов Microsoft KEK и db.** Ручное добавление этих сертификатов особенно актуально на некоторых системах с **AMI BIOS/UEFI**. В более новой прошивке необходимые сертификаты уже могут присутствовать, поэтому повторное добавление может не требоваться. Проверяйте фактические записи прошивки, а не полагайтесь только на производителя или возраст прошивки. В [руководстве Microsoft по истечению срока действия сертификатов Secure Boot и обновлению CA](https://support.microsoft.com/en-us/servicing/os/secure-boot/2025/06/windows-secure-boot-certificate-expiration-and-ca-updates) описан переход.

Когда обновление необходимо, загрузите открытые сертификаты DER из репозитория Microsoft, скопируйте их на USB-накопитель, читаемый прошивкой, и с помощью меню управления ключами Secure Boot **добавьте** их в указанные хранилища, сохранив существующие записи:

- **KEK** — [`microsoft corporation kek 2k ca 2023.der`](https://github.com/microsoft/secureboot_objects/tree/main/PreSignedObjects/KEK/Certificates). Это сертификат Key Exchange Key для авторизации обновлений базы данных Secure Boot.
- **db** — из [каталога сертификатов Microsoft db](https://github.com/microsoft/secureboot_objects/tree/main/PreSignedObjects/DB/Certificates):
  - `windows uefi ca 2023.der` — загрузчики Windows;
  - `microsoft option rom uefi ca 2023.der` — сторонние option ROM;
  - `microsoft uefi ca 2023.der` — сторонние загрузчики и приложения EFI.

На практике добавления **только `windows uefi ca 2023.der` в db** достаточно, чтобы загрузился диспетчер загрузки Windows, подписанный этим CA, при условии, что остальная часть его цепочки загрузки доверена и не отозвана. Другие сертификаты db охватывают сторонние загрузчики, приложения EFI и option ROM; сертификат KEK предназначен для обновлений базы данных. Тест загрузки только Windows не доказывает, что будут работать эти остальные компоненты или будущие обновления сертификатов.

Добавляйте только сертификаты, подходящие для машины. Не заменяйте весь KEK или db, не удаляйте записи об отзыве из dbx и не помещайте сертификаты Microsoft KEK/db в слот PK. Меню прошивки и принимаемые форматы файлов различаются; следуйте инструкциям производителя, если прямой импорт DER не поддерживается.

После запуска Windows проверьте из сеанса Windows PowerShell с повышенными правами:

```powershell
Confirm-SecureBootUEFI
```

Результат должен быть **`True`**. Затем проверьте значение в действующем реестре:

```powershell
Get-ItemPropertyValue -LiteralPath 'HKLM:\SYSTEM\CurrentControlSet\Control\CI\Protected' -Name 'CustomKernelSignerLockedEnabled'
```

Результат должен быть **`1`**. Если какая-либо проверка не проходит, исправьте конфигурацию системы/прошивки до попытки загрузить драйвер. Эти проверки являются обязательными условиями, а не доказательством того, что конкретный файл `.sys` будет принят Code Integrity ядра Windows.

### 6. Соберите и подпишите драйвер

Соберите и подпишите файл `.sys` с помощью:

```powershell
& 'C:\portmaster_v3\windows_kext\build-signed.bat'
```

Пакетный файл переходит в собственный каталог, собирает `driver\target\x86_64-pc-windows-msvc\release\driver.lib` с помощью `cargo build --release`, инициализирует среду x64 Visual Studio, генерирует/компилирует ресурс версии и вызывает `link-dev.ps1` для компоновки и подписи **`C:\portmaster_v3\windows_kext\portmaster-kext.sys`**.

Текущая команда подписи в `link-dev.ps1` использует:

- **`localhost-km.pfx`**, субъект **`Localhost Kernel Mode Driver Certificate`**, для подписи драйвера;
- **`localhost-root-ca.der`** как дополнительный сертификат цепочки;
- пароль PFX **`1`**, SHA-256 и службу меток времени DigiCert.

Храните эти файлы в `windows_kext` либо намеренно обновите команду подписи при использовании других расположений/паролей. `localhost-pk.pfx` подписывает политику на шаге 2, **а не** драйвер. Пакетный файл собирает/подписывает драйвер; он не регистрирует ключи прошивки, не активирует `CustomKernelSigners`, не развёртывает политику и не загружает драйвер.

Успешная операция сборки/подписи или даже успешная проверка Authenticode командой `signtool verify /pa` не доказывает, что Code Integrity ядра Windows примет драйвер. Используйте приведённый ниже ограниченный по времени запуск монитора, чтобы проверить фактическую загрузку при настроенной политике. Проверка цепочки Authenticode также зависит от доверия в хранилище сертификатов; пользовательская настройка допуска ядра определяется подписанной политикой и зарегистрированным PK, а не только обычным хранилищем сертификатов.

### Модульные тесты и C++ клиент

Запустите модульные тесты драйвера из Git Bash с помощью:

```bash
cd /c/portmaster_v3/windows_kext/driver && RUSTFLAGS="" cargo test --release
```

Соберите C++-клиент/монитор из PowerShell с помощью:

```powershell
& 'C:\portmaster_v3\kext_client\build.bat'
```

При стандартной сборке Ninja монитор находится в `C:\portmaster_v3\kext_client\build\kext_monitor.exe`. Если CMake переключится на многоконфигурационный генератор, исполняемый файл может находиться в `build\Release`. Запускайте его **от имени администратора**, всегда с **`--duration`** для ограниченного теста и с явным путём к драйверу:

```powershell
& 'C:\portmaster_v3\kext_client\build\kext_monitor.exe' --duration 10 'C:\portmaster_v3\windows_kext\portmaster-kext.sys'
```

Монитор сам создаёт/запускает службу драйвера, открывает устройство и при обычном завершении закрывает устройство, останавливает/выгружает драйвер и удаляет его службу. **Не создавайте службу вручную.** Вердикт по умолчанию — `PermanentAccept`; избегайте глобальных вердиктов блокирования/отбрасывания для первоначальной проверки. Дождитесь завершения выполнения по таймеру и очистки; не завершайте процесс принудительно и не останавливайте его службу, пока дескриптор устройства открыт. Не запускайте монитор без ограничения продолжительности для автоматических тестов без присмотра.
